# Выкладка лендинга IGRAI на сервер

Сайт статический: nginx отдаёт файлы сам, никакой Node на сервере не нужен.
Целевой адрес — `http://193.9.60.14/igrai2/`

## Быстрый запуск

**Windows:** двойной клик по `3-deploy.bat` в корне проекта.
Он найдёт Git Bash (идёт вместе с Git для Windows) и запустит `deploy/deploy.sh`.

**Linux / macOS / Git Bash вручную:**

```bash
chmod +x deploy/deploy.sh
./deploy/deploy.sh
```

## Настройки

Всё в `deploy/target.env` (этот файл в `.gitignore`, адрес сервера в репозиторий
не уезжает):

| переменная   | по умолчанию     | что это                                          |
|--------------|------------------|--------------------------------------------------|
| `SSH_HOST`   | `193.9.60.14`    | IP сервера                                       |
| `SSH_USER`   | `root`           | пользователь SSH                                 |
| `SSH_PORT`   | `22`             | порт SSH                                         |
| `SITE_PATH`  | `/igrai2`        | подпуть, по которому открывается сайт            |
| `REMOTE_DIR` | пусто            | папка на сервере; пусто = определить автоматически |

**Как всё устроено на этом сервере.** В `/etc/nginx/sites-available/igrai`
один server-блок на 80-м порту, его корень — `/var/www/igrai`, там лежит
старый лендинг. Из-за `try_files $uri $uri/ /index.html` любой неизвестный
адрес отдаёт его `index.html` — с кодом **200**, а не 404.

Поэтому просто положить файлы в `/var/www/igrai2` мало: nginx туда не смотрит.
Нужен отдельный блок `location ^~ /igrai2/` с `root /var/www` — тогда адрес
складывается в `/var/www/igrai2/`. Такой блок лежит в `deploy/nginx-igrai2.conf`,
и `deploy.sh` ставит его сам (с резервной копией конфига, `nginx -t` и откатом,
если проверка не пройдёт). Ровно так же на этом сервере уже сделано для `/1comp/`.

`^~` в блоке обязателен: он запрещает nginx проверять regex-локации, иначе
картинки и шрифты перехватил бы блок с кэшем и стал бы искать их от корня
`/var/www/igrai`.

## Доступ по SSH

Скрипт не спрашивает пароль и ничего не хранит — авторизацией занимается сам `ssh`.
Удобнее один раз положить на сервер свой ключ:

```bash
ssh-keygen -t ed25519          # если ключа ещё нет
ssh-copy-id root@193.9.60.14   # в Git Bash работает
```

После этого выкладка идёт без ввода пароля.

## Что делает deploy.sh

1. **Проверяет проект локально** — есть ли `index.html`, `assets/`, шрифты,
   `three.js` и модель `asus_rog_animated.glb`. Если чего-то нет, останавливается
   до подключения к серверу.
2. **Проверяет связь** и печатает имя сервера и версию ОС.
3. **Готовит сервер:** ставит nginx, если его нет, создаёт `/var/www/igrai2`.
4. **Заливает файлы** потоком `tar` через ssh — без `rsync`, которого нет в Git Bash
   на Windows. Сначала во временную папку `igrai2.new`, потом одним `mv` подменяет
   боевую. Сайт никогда не бывает обновлённым наполовину.
5. **Проверяет результат** — и не по коду ответа. У nginx в конфиге `landing1`
   стоит `try_files $uri $uri/ /index.html`: при неверном пути он отдаёт чужой
   `index.html` с кодом **200**, и снаружи это выглядит как «сайт открылся,
   но без стилей». Поэтому скрипт ищет в ответе маркер нашей страницы,
   проверяет, что `style.css` приходит с `Content-Type: text/css`, а не
   `text/html`, и что модель весит больше мегабайта.
6. **Если проверка не прошла** — показывает блок для nginx, спрашивает согласия
   и ставит его: резервная копия конфига, вставка перед `location / {`,
   `nginx -t`, `reload`. При ошибке в конфиге откатывает копию обратно.
   Повторный запуск ничего не дублирует — блок ставится один раз.

Есть ещё `deploy/diagnose.sh` (и `4-diagnostika-servera.bat`): только читает
сервер и складывает отчёт в `deploy/server-report.txt`. Ничего не меняет.

Права выставляются сами: папки `755`, файлы `644`, владелец `www-data`.

## Что заливается

`index.html`, `README.md`, папка `assets` целиком, `asus_rog_animated.glb`.

Не заливается: `.git`, батники, `deploy/`, `target.env`, системный мусор Windows.

## Обновить сайт

Поменяли что-то — запустили `3-deploy.bat` снова. Всё.

## Если что-то не так

```bash
# логи ошибок nginx
ssh root@193.9.60.14 'tail -30 /var/log/nginx/error.log'

# что реально лежит на сервере
ssh root@193.9.60.14 'ls -la /var/www/html/igrai2'

# отдаётся ли страница с самого сервера
ssh root@193.9.60.14 'curl -I http://127.0.0.1/igrai2/'
```

Частые случаи:

* **403 Forbidden** — права на файлы. Скрипт их выставляет, но если правили
  руками: `chmod -R 755 /var/www/html/igrai2`.
* **Открывается чужой сайт / «слетели стили»** — файлы легли мимо корня nginx.
  Скрипт теперь ловит это сам и пишет «ФАЙЛЫ ЗАЛИТЫ, НО САЙТ ОТДАЁТСЯ НЕВЕРНО».
  Посмотрите `ssh root@193.9.60.14 "nginx -T | grep -n root"` и впишите нужный
  путь в `REMOTE_DIR`.
* **Страница есть, ноутбука нет** — не отдалась модель. Проверьте, что
  `asus_rog_animated.glb` доехал целиком (13 МБ):
  `ls -l /var/www/html/igrai2/asus_rog_animated.glb`.

## Когда появится домен

Пока сайт работает по IP и по HTTP. Появится домен — направьте A-запись на
`193.9.60.14`, потом на сервере:

```bash
apt install -y certbot python3-certbot-nginx
certbot --nginx -d ваш-домен.ru -d www.ваш-домен.ru
```

Certbot сам выпустит сертификат, настроит редирект с HTTP и автопродление.
В папке `landing1/deploy` лежат готовые `nginx.conf` с TLS и HSTS и
`nginx-limit.conf` — их можно взять за основу, если захотите вынести сайт
в корень домена вместо подпапки.
